# 新規モンスター実装手順書（ゼロから作成・ドラフト）

> **本ドキュメントの位置づけ**: `mhdp_monster_valk` の旧→新形式移行で確立した知見（`ai_docs/monster/migration/monster_migration_playbook.md`）を土台に、**旧コードが存在しないゼロからの新規モンスター実装**向けに手順を再構成したもの。
> **ドラフト版**: まだこの手順書自体で新規モンスターを1体も作っていない段階の初版。実際に1体作り切った時点で、想定と食い違った箇所を修正すること。

## 移行(migration) との決定的な違い

`ai_docs/monster/migration/monster_migration_playbook.md` の Stage 構成・API カタログ（`apply_attack.m` 系、`alignment_start.m`、`vector_move` 系、`assets:object` システム、`.mcfunction` 記法ルール等）は**そのまま再利用する**。違うのは「何を根拠に値・構造を決めるか」。

| | 移行（migration） | 新規作成（このドキュメント） |
|---|---|---|
| 判定サイズ・フレーム窓の根拠 | 旧コードの実装値（近似元がある） | 存在しない。仕様書の指定 or 類似モンスターからの提案 |
| frame番号・ロケータ名の入手 | `mhdp_monster_<name>_bak` の event ファイルから読める | AJ blueprint 側にしか存在しない。**`animated_java_<name>/` は移行時と同様 Read/Grep 禁止**なので、仕様書に明記されていなければ読み取れない |
| 「正解」の存在 | 旧コードの再現が正解の目安になる | 正解が無い。仕様書とユーザーの実機確認がすべて |
| バグの主因 | 旧コードのコピペミス・dead code | 仕様書の解釈違い・記載漏れ、Claude側の想像による埋め合わせ |

このため新規作成では、**「旧コード」の代わりに「仕様書」を一次情報源として扱う**運用に切り替える。仕様書に無い情報は想像で埋めず、ユーザーに確認するか、仮値であることを明記した上で提案する。

## 0. 事前準備

1. **Uid 採番**: `mhdp_core` 側で未使用の Uid を確認して割り当てる（既存: 1001=ranposu, 1003=dino, 1004=valk 等）。ObjectId 帯（`<Uid下4桁>0`〜）も同時に予約する。
2. **AJ blueprint の作成**（ユーザー側作業）: Blockbench + Animated Java でモデル・ボーン・ロケータ・アニメーションを作成する。
   - ロケータ命名は新形式の規約に合わせる（`pos_` で始まるもの → `at_locator` で参照、それ以外 → `as_locator`）。命名を最初からこの規約に沿わせておくと実装時の混乱が減る。
   - 最低限、最初のバッチで実装するアニメーショングループ分は先にエクスポートしておく（全アニメ完成を待つ必要はない。後続バッチ分は都度追加エクスポートでよい）。
3. **仕様書（content spec）の作成**: `monster_spec_template.md` を参照し、`ai_docs/monster/<name>/spec.md` として作成する。**Stage 1 着手前に、最低でも基本情報・部位構成・攻撃一覧の骨子ができていること**が望ましい（アニメーション詳細は Stage 5 の各グループ着手前に順次埋めても良い）。
4. 進捗トラッカー `ai_docs/monster/<name>/creation_progress.md` を用意する（`migration_progress.md` と同形式。移行版との違いは「旧コード引用」の代わりに「仕様書のどの記述に基づくか」「未確定の仮値」を書き残す点）。

## 1. Stage 構成

`ai_docs/monster/migration/monster_migration_playbook.md` §1 の Stage 1〜6 と同じ区分をそのまま使う。以下は新規作成特有の差分のみ記す。

### Stage 1〜4（register / summon・init / tick骨格 / damage・reaction・break）
- 内容は仕様書の「基本情報」「部位構成」「行動選択ロジック（距離帯・重み）」節から直接起こす。
- 部位破壊・肉質変化などのゲームデザイン的な数値（耐久値・閾値）は仕様書に無ければ**仮値で埋めず、ユーザーに確認する**（旧コードという裏付けが無いため、Claude の想像値がそのままゲームバランスになってしまう）。
- AttackData の左右分岐・技名は仕様書の「攻撃一覧」節からそのまま転記する（命名の揺れが起きないよう、この段階で確定させる）。

### Stage 5（event/* アニメーショングループ）— 最大の違い
詳細は §2 を参照。旧コードの「変換」ではなく仕様書の「実装」になるため、進め方を作り直す。

### Stage 6（util/models/phase/debug/advancement, 弾/VFX）
- `core/util/models/*` のモデルIDは、AJ側のモデル名が仕様書または口頭確認で分かるまで仮プレースホルダで先に進めてよい（移行時と同じ運用）。
- `assets:object/` の新規 VFX/弾は、既存の共有オブジェクト（`0016.ground_crack` 等、モンスター非依存の汎用もの）を流用できないか先に確認する。流用できないものだけ新規 ObjectId を採番して実装する。

## 2. Stage 5: アニメーショングループ実装の進め方（新規作成版）

### 2.1 基本方針
移行時の「複雑グループのみ4段階運用」という区分けを緩め、**新規作成では単純グループでも実装前に軽い確認を1回挟むことを基本とする**。理由: 旧コードという「答え合わせの対象」が無いため、Claude が仕様書を読み違えたまま実装してしまうとそれが唯一の実装として確定してしまう。移行時よりも早い段階でのすり合わせが事故を減らす。

複雑グループ（複数 object を使う、特殊な判定パターン等）の4段階運用（計画→main/end/移動→演出→攻撃判定）は移行時と同じ枠組みをそのまま使う。

### 2.2 標準フロー（1グループあたり）
1. **仕様書の該当グループ記述を読む**。frame番号・ロケータ名・判定形状の記載が不足していれば、**想像で埋めずにユーザーに質問する**。埋められる項目とユーザー確認が必要な項目を切り分けて聞く。
2. **実装計画を提示**（判定形状の初期提案値、使用object、移動方式、軸合わせの有無）。特に「初出の数値」（判定サイズ・フレーム窓）は根拠（類似モンスターのどの技を参考にしたか等）を添えて提示し、承認を得る。
3. **main/end/移動を実装** → **必ず実機でアニメーション再生を確認**（旧コードの裏付けが無いため、この確認を省略しない）。
4. **演出（object）実装**。新規VFXが必要な場合は Stage 6 の object 実装を並行して行う。
5. **攻撃判定を実装**。`cuboid_preview.m` は生成時点でコメントアウトせず有効なまま残し（[[cuboid-preview-debug-uncommented]]）、実機調整はユーザーに委ねる。

### 2.3 数値提案の根拠付け
新規モンスターには「近似元となる旧の判定サイズ」が存在しない。初回提案値を出す際は、以下の優先順位で根拠を示す:
1. 仕様書に明記された値（あればそれを最優先）
2. 体格・技の性質が近い既存モンスター（dino/ranposu/valk）の類似技の実装値
3. 上記どちらも無ければ「仮値である」ことを明記した上で提案し、実機確認前提とする

根拠を毎回一言添えることで、ユーザーが妥当性を判断しやすくなる。

### 2.4 反復調整を前提にする
移行と異なり、新規モンスターは全ての値が初出であるため、1回の実装で確定させようとしない。実機テスト→数値調整→再確認のループが標準フローの一部である前提で進める。トラッカーには「仮値」と「確定値」を明確に区別して記録する（例: `Scale:4.0（仮、要実機調整）` → 確定後に `Scale:4.0（確定・2026-XX-XX）`）。

## 3. よくあるつまずきパターン（新規作成特有）

移行時のバグパターン（`ai_docs/monster/migration/monster_migration_playbook.md` §5）はコピペミス由来が中心だったが、新規作成では性質が異なる:

1. **仕様書の記載漏れをClaudeが想像で埋めてしまう**: frame番号・ロケータ名など、仕様書に書かれていない情報を「dinoならこうだろう」で埋めると、実際のAJアニメーションと一致しないまま実装が進んでしまう。不明点は都度質問する。
2. **仕様書とAJ blueprintの不整合**: 仕様書執筆時点と実際のAJエクスポート後でロケータ名・アニメーション名が変わっていることがある（ユーザー側の作業順序次第）。実装直前に「このグループのロケータ名は仕様書記載のままで合っているか」を確認する一手間が安全。
3. **左右対称技の実装忘れ**: 移行では旧コードに両方揃っていたが、新規作成では仕様書が片方しか書かれていないことがある（左右対称なので省略した、等）。対称技かどうかを仕様書執筆時点で明示してもらう（§4のテンプレ参照）。
4. **判定サイズの過大/過小**: 根拠となる旧実装が無いため、初回提案が的外れなことがある。§2.3の根拠提示と、コメントアウトしない `cuboid_preview.m` 運用でカバーする。

## 5. 次モンスター作成時にこのドラフトを見直す観点

- このドキュメントはまだ実地検証（実際に1体を新規作成し切る）を経ていない。特に §2（標準フロー）・§2.3（数値提案の根拠付け）は理屈上の設計であり、実際にやってみると往復回数やユーザー確認の粒度が想定と違う可能性が高い。
- 仕様書テンプレート（`monster_spec_template.md`）に対しても、実際に書いてもらった結果「この項目は不要だった」「これが足りなかった」というフィードバックを反映して改訂する。
